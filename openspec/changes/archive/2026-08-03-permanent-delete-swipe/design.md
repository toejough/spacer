## Context

Cards render via `container.innerHTML = items.map(render...Card).join('')` on every `loadTodos`/`loadNotes` call — the DOM is fully rebuilt each refresh, so per-card event listeners would need re-attaching constantly. No touch/swipe/pointer gesture code exists anywhere in `srv/static/script.js` today; this is the first. The edit modal already has a pattern for a state-conditional secondary action (`updateModalAbandonButton`, toggling one button's text/handler between Abandon and Reopen) that a new "Delete Forever" control can sit alongside. See proposal.md - Why.

## Goals / Non-Goals

**Goals:**
- Swipe-to-delete works reliably on Done/Abandoned cards without fighting vertical list scrolling.
- The undo window is a real safety net, not just decorative — the deleted item must be fully recoverable state (including cloze_data) until the window expires.
- Keyboard/screen-reader users have a complete, independent path to the same capability.

**Non-Goals:**
- No change to Abandon/Reopen/Done semantics — this only adds a new terminal action beyond them.
- No bulk delete / multi-select — one card at a time, matching how every other action in the app already works.
- No server-side or backup-aware behavior — deletion only touches the client-side `localStorage` array, exactly like every other mutation in this app.

## Decisions

- **Event delegation on the list container, not per-card listeners.** Attach one `pointerdown`/`pointermove`/`pointerup` (or `touchstart`/`touchmove`/`touchend`) set on `#todoList`/`#noteList` itself, using `event.target.closest('.item-card')` to find the card and its `data-id`. Survives the innerHTML rebuild on every refresh without re-registration.
- **Swipe-left-only, not bidirectional.** Only a leftward drag (`dx < 0`) past the deadzone-and-ratio check engages the gesture; a rightward drag is left alone, same as a vertical one. This is the standard convention (reveal actions on the right, per the swipe-to-delete research above) and — practically — it's what makes a single reveal panel work at all: the panel's trash icon has one fixed position (centered in the final revealed strip), which only reads correctly if the card always vacates space in the same direction.
- **`touch-action: pan-y` set statically in CSS, not toggled by JS.** Initially the JS added `touch-action:none` to the card only once its own horizontal/vertical ratio check decided the gesture was a swipe (`|dx| > |dy| * 1.5` past a small deadzone) — but that's too late: browsers commit to scroll-vs-custom-gesture ownership from the very first pixels of a touch sequence, based on whatever `touch-action` the element already had at touch-start, not on anything JS decides mid-gesture. By the time the JS ratio check fired, the browser had frequently already claimed the gesture as a scroll and canceled the pointer sequence — which surfaced as two real bugs: pure vertical scrolling sometimes committed a delete (see the `pointercancel`-vs-`pointerup` fix below), and even after that fix, vertical motion still felt like it "canceled the swipe" unpredictably. Setting `touch-action: pan-y` statically fixes this at the source: it tells the browser, permanently, that vertical panning on these cards is always native and horizontal panning is always excluded from native handling, so the browser's own arbitration — not a JS race — decides which gesture a given touch sequence is. Verified with real touch input dispatched via CDP's `Input.dispatchTouchEvent` (synthetic DOM events don't trigger this arbitration at all, so a real touch pipeline was necessary to catch and confirm the fix).
- **`pointercancel` must never commit a delete, only `pointerup` can.** Split the single end-of-gesture handler into `releaseGesture` (bound to `pointerup` — commits if past threshold, else snaps back) and `abortGesture` (bound to `pointercancel`/`pointerleave` — always snaps back, regardless of how far the drag had already gone). `pointercancel` fires whenever something else takes ownership of the gesture (most commonly the browser handing off to native scroll); treating it the same as a deliberate release meant an already-armed swipe that got interrupted by scrolling would still delete the item — the opposite of what an interruption should mean.
- **Swipe only arms on Done/Abandoned cards.** The gesture handler checks the card's state before engaging — on Open cards, no drag transform or delete affordance triggers at all, so there's no accidental exposure of a destructive action where it isn't valid.
- **Undo via a short-lived "pending delete" buffer, not immediate array mutation.** On threshold-cross: remove the item from the rendered list immediately (visually gone) and hold its full object in memory with a timer (not yet written to `localStorage`). Only on timer expiry does it actually get removed from the saved array; activating Undo before then just re-renders from the still-intact stored data. This makes "restore" trivial and exact — no partial-delete/partial-write states are ever persisted.
- **"Delete Forever" in the edit modal is a separate button from the existing Abandon/Reopen toggle**, not folded into it — it's a distinct, more severe action and conflating it with the existing one-button-two-labels pattern would blur that distinction. Shown/hidden by the same `done`/`archived` state check `updateModalAbandonButton` already does, in a sibling function.
- **Reveal-behind panel, not just card-tint.** Research into current swipe-to-delete conventions (iOS Mail/Reminders-style patterns, per LogRocket's "Designing swipe-to-delete and swipe-to-reveal interactions" and DesignMonks' delete-button UI guidance) confirms the dominant pattern is a red panel with a trash icon revealed *behind* the card as it slides — "like sliding a drawer open" — not just tinting the moving card itself. Implemented as `wrapWithSwipeReveal`: eligible cards (Done/Abandoned todos, Abandoned notes) get wrapped in a `position:relative` `.item-card-wrapper` containing an absolutely-positioned `.swipe-reveal` (red background + centered trash icon) sitting behind the card in DOM order, so it's exposed in the space the card vacates as it translates. Ineligible cards render unwrapped — no reveal markup exists for them at all, consistent with the existing "swipe never arms on Open/active cards" rule. The card's own progressive background tint (`.swiping` → `.swipe-armed`, from the prior iteration) is kept alongside this, not replaced — both signal delete-intent together: the card getting redder as you drag it, and a solid red trash-icon panel revealed underneath.

## Risks / Trade-offs

- [The JS deadzone/ratio check still governs mouse and pen input, where `touch-action` doesn't apply, so a fast diagonal drag with a mouse could still misfire] → the deadzone + ratio threshold is tunable at implementation time; err toward requiring a clearer horizontal signal (favor missed swipes over accidental deletes, since Undo doesn't help if the swipe wasn't even the user's intent). Real touch input is the primary target and is now handled by `touch-action: pan-y` rather than this JS check alone.
- [Holding a pending-delete item only in memory means a page reload during the undo window loses the undo option (though not the delete itself, since it hasn't persisted yet — the item just never actually left storage)] → acceptable: on reload, the timer never ran, so the item reappears as if nothing happened. This is actually the safer failure mode, not a data-loss risk.
- [No confirm step on swipe threshold-cross, per your explicit choice] → the Undo toast is the entire safety net for the touch path. If the toast duration turns out too short in practice, that's a one-line implementation-time tuning fix, not a design change.

## Migration Plan

1. Add `deleteItemPending`/`commitDelete`/`undoDelete` logic and the swipe gesture handler in `srv/static/script.js`.
2. Add `data-id` attributes to rendered cards (needed for delegation to resolve which item a gesture/click targets) if not already present.
3. Add the "Delete Forever" button + `updateModalDeleteButton` (or equivalent) wired into `openEdit`/`onEditTypeChange` alongside the existing `updateModalAbandonButton` call.
4. Add undo-toast markup/CSS.
5. Verify: swipe threshold on a Done todo, an Abandoned todo, an Abandoned note; verify Open cards never arm the gesture; verify Undo restores exactly; verify toast expiry actually removes the item from `localStorage`; verify keyboard path via the edit modal for both item types. The underlying delete/undo/gating logic was verified with a VM-harness script; the actual pointer-drag DOM interaction and touch-action-based scroll disambiguation were verified with a real headless browser (Playwright/Chromium) driving both mouse gestures and, for the touch-specific arbitration, real touch input via CDP's `Input.dispatchTouchEvent`.
6. Rollback: revert the commit — no data migration, since nothing about existing item shapes changes.
