# Retro: #1 Bootstrap — Pass

## Plus (reinforce/repeat)

**Process:**
- Plan review caught 12 real issues before a single line of code was written. The spec reviewer earned its keep — TDD gaps, missing stubs, wrong commit trailers. Fixing a plan is cheap; fixing code is expensive.
- Atomic commits with clear messages. Every task = one commit. Easy to bisect, easy to revert.
- Subagent-per-task kept context clean. No implementer was confused by prior task state.

**Structural:**
- SM-2 as a pure function was the right call. Zero dependencies, trivially testable, can be swapped later without touching anything else.
- Dexie typed with EntityTable gives us type-safe DB queries from day one.
- Lazy-loaded routes for DeckView and ReviewView — correct default for a PWA.

## Delta (change next time)

**Process:**
- The brainstorming → spec → plan → review → re-review → execute pipeline was massively heavy for a scaffold. We spent more time on process than on code. For a bootstrap, a lighter flow would have been fine: sketch the plan, execute it, review the result. Save the heavy process for feature work with real design decisions.
- Skipped code quality reviews "because it's generated code" — fair for Task 1 but set a bad precedent. Should have done at least one quality review pass at the end covering the full implementation.

**Structural:**
- **Horizontal layers before vertical slices was a mistake.** We built DB, stores, router, SM-2, PWA, components — all disconnected. The result is an app that passes 16 tests and does absolutely nothing. A better bootstrap would have been: scaffold → one working flow (create deck, add card, review it) → then fill in the rest. The current approach front-loaded architecture and deferred usability.
- Store stubs are empty shells that don't query the DB. Component stubs are empty divs. These aren't really "stubs" — they're placeholders that will be completely rewritten. The work of creating them was largely wasted.
- No integration tests. Unit tests on isolated pieces gave false confidence. Every piece works alone; nothing works together.
- Issue #3 (add cards) is now redundant with #5 (wire up core flow). The backlog got ahead of the codebase — we filed feature issues before the app had basic functionality.

**Visual:**
- The app is a white header on a gray page with placeholder text. It doesn't feel like anything yet. For a bootstrap, that's acceptable — but the gap between "all tests pass" and "a person can use this" is larger than it should be. Next time, the bootstrap AC should include "a user can complete one full action."

## Other observations

- `--legacy-peer-deps` was needed for every npm install after Tailwind. The `@tailwindcss/vite` package hasn't declared Vite 8 support. This is cosmetic but will confuse future contributors. Worth pinning or documenting.
- The 5-minute increment skill wasn't used for the bootstrap itself. That's by design (bootstrap is allowed to exceed 5 min), but it means the skill is untested. The first real increment will be the real test of the workflow.
- No project-level CLAUDE.md exists yet. Should create one with build commands, test patterns, and conventions so future sessions don't have to rediscover them.
- The `--localstorage-file` warning in test output is noise from happy-dom. Should be suppressed or the environment config fixed.
